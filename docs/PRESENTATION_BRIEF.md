# Прототип Claude Code desktop: как работать с ИИ-агентами над несколькими задачами сразу

Материал для подготовки презентации. Описывает разделы, фичи, связи между ними, логику работы и ключевые решения с причинами. Источники правды — `docs/INBOX.md`, `docs/CHAT_LEVELS.md`, `docs/BRIEF_AND_PLAN.md`; этот файл — их сжатый пересказ для рассказа.

---

## 0. Контекст проекта в одном абзаце

**Что это.** Кликабельный прототип десктопного приложения Claude Code (React 19 + Vite + TypeScript + Tailwind v4). Базой стала точная копия (1:1) существующего прототипа Alloy на дизайн-системе Claude (токены `--cds-*`, иконки Anthropicons). Поверх неё за два дня (25–26 сентября 2026) спроектировали и собрали новый слой продукта.

**Проблема.** Разработчик или техлид ведёт несколько задач параллельно, над каждой работают ИИ-агенты. Сегодня это набор чатов: непонятно, какой агент стоит и ждёт человека, что именно от него нужно, сколько стоит решение и можно ли доверять словам агента «я всё сделал».

**Ответ прототипа — четыре связанные части:**
1. **Up next** — экран «в какую задачу идти первой».
2. **Уровни задачи в чате** — чат остаётся чатом; план виден у любой задачи, бриф — когда агенту есть что сказать, а согласования появляются, только когда задача этого заслуживает.
3. **Plan и Brief** — панель рядом с чатом: что агент сделает, во что обойдётся и как он понял задачу.
4. **Приёмка результата** — граница между «агент сказал, что сделал» и «это проверил кто-то другой».

И всё это держится на **одной модели задачи и одном состоянии**: решение, принятое в одном месте, мгновенно видно везде.

- Репозиторий: `github.com/ededdyeddd/claude-code-prototype`, деплой на GitHub Pages (`npm run deploy`).
- Около 150 коммитов за два дня, работа велась в ветках-фичах с мерджами в `main`.

## 1. Сквозные принципы (на них держатся все решения)

Хороший кандидат на отдельный слайд: каждое решение ниже выводится из этого списка.

1. **Отвечает на вопрос и отпускает.** Up next — оглавление, а не место для переписки. Он не приглашает сидеть и смотреть.
2. **Одно решение — одна карточка и одно состояние.** Вопрос агента отвечается одной и той же карточкой в Up next и в чате; ответ в одном месте закрывает его везде. Списки, сайдбар и уведомления только указывают на задачу.
3. **Решение с открытыми глазами.** До ответа видно, что изменится в плане (что добавится, что уйдёт), сколько это стоит и сколько займёт.
4. **Прогноз всегда подписан.** У любой оценки есть источник («по 12 похожим задачам», «оценка агента»). Прогноз помечен «~», факт — без знака. Время — это время работы агента, а не срок.
5. **Один акцентный цвет — терракота (`--cds-clay`), и значит он только «нужен ты».** Статусы различаются формой (точка, пульсирующая точка, кольцо), а не цветом. Зелёного и красного нет (исключение — дифф файлов).
6. **Тише со временем.** Интерфейс не дублирует одно и то же и не выделяет то, что не требует действия. Онбординг показывается один раз.
7. **Слова агента — не факт.** Сделанное показываем как итог с доказательствами, будущее — как намерение. Отмечает агент с доказательством, а не человек чекбоксом (кроме ручных проверок при приёмке).

**Единая система форм статуса** (в списке, сайдбаре, плане, брифе):
- терракотовая точка — нужен ты;
- серая пульсирующая — идёт работа;
- серая закрашенная — готово;
- пустое кольцо — впереди.

Галочек, ромбов у гейтов и значков паузы нет: их пробовали и убрали ради одной системы. **Одно осознанное исключение** — приёмка результата (§6): там галочка стоит только у того, что доказал внешний источник.

## 2. Карта приложения и связи

```
Сайдбар ──────────────┬─ Up next (список задач) ──── Панель задачи (Plan | Brief)
  • New                 │    Blocked / Can wait / Running        ▲
  • Up next ●           │                                        │ тот же PlanPane
  • Artifacts           │                                        │
  • Routines            └─ Чат задачи ─────────────── Панель задачи (Plan | Brief)
  • Customize                 лента + живой статус         (на приёмке + Result | Diff)
  • проекты → чаты ●          панель решений над композером (DecisionDock)
  • лимит недели, аватар со статусом внимания
```

**Как части связаны:**
- **Одна модель `Task`** (`src/data/task.ts`) для Up next и чата: этапы → шаги → гейты, вопросы с вариантами, бриф, результат.
- **Одно состояние.** Ответы хранятся как `answers[taskId:questionId]`; группы Up next, счётчики, точки в сайдбаре, статус в чате и карточки вопросов вычисляются из них. Два стора: `inboxStore` (ответы, режим внимания, группы) и `chatTaskStore` (допущения, запуск, правки, эскалация, приёмка). `deriveTask()` / `liveTask()` дают задачу «как она есть сейчас», и ими пользуются обе стороны.
- **Один компонент плана** (`PlanPane`) рисует план и в Up next, и в чате.
- **Одна форма решения.** Вопрос, допущение, гейт, эскалация и приёмка выглядят одинаково: как панель вопроса Claude Code.
- **id чата задачи = id задачи**, поэтому сайдбар, Up next и чат указывают на одно и то же.

**Пример сквозного сценария (удобен для демо):** в Up next задача в Blocked → открываешь панель → видишь вопрос на шаге плана с ценой и обратимостью вариантов → выбираешь вариант, и план ниже перестраивается (New / Removed) → «Answer» → задача уходит из Blocked, точка в сайдбаре гаснет, в чате под вопросом агента появляется «You: …».

## 3. Раздел Up next (бывший Inbox)

**Вопрос, на который отвечает:** «в какую задачу идти первой». Маршрут `/up-next`.

### 3.1. Структура экрана
Три колонки: сайдбар, список задач, боковая панель задачи. Панель открывается по клику, как артефакт в Claude. Обе боковые колонки меняют ширину, и ширина запоминается.

### 3.2. Шапка
- Заголовок serif.
- **Режим внимания** (кнопка справа): «You're available», «You're busy until 18:00», «Do not disturb», время Busy выбирается прямо в меню. Режим влияет только на уведомления и **не приглушает список** (открыл страницу — значит готов разбирать).
- Итог «3 blocked · 2 can wait».
- **Сводка «While you were away, 14:00–16:00 · 5 checks passed · 12 auto-decided · $10.87 spent».** Каждая цифра кликабельна и открывает список: проверки, решения агентов с «Change», расходы по задачам. Цифры считаются из данных задач, поэтому совпадают со списками.

### 3.3. Группы задач
- **Blocked** — задача ждёт тебя (терракотовая точка). Шаги, которым ответ не нужен, могут идти параллельно: во второй строке «1 question · 2 in parallel».
- **Can wait** — ты не держишь агента: вопрос есть, но агент работает дальше (серая пульсирующая точка), или агент закончил и результат ждёт приёмки (серая неподвижная точка, «accept the result»).
- **Running** — идёт без тебя; справа «Your turn by 17:30» с источником прогноза.
- Группы сворачиваются, пустые скрываются. Если никто не нужен, на экране «Nothing needs you» и «Coming up for you».

**Строка задачи (две строки):** название · сколько ждёт (факт) | проект · этап · что нужно от тебя («1 question», «1 assumption to confirm», «approve the brief and plan», «split into stages?», «accept the result») · агент · потрачено.

### 3.4. Панель задачи
- Шапка как в чате: название, описание, табы Plan | Brief, «Open task».
- Одна строка меты: «2 questions · storefront · feat/checkout · $4.20 spent · 1h 2m». Клик по «2 questions» прокручивает к вопросу.
- **План** по этапам (заголовки закреплены, завершённые свёрнуты, прогресс и сумма этапа); шаги на вертикальной линии; готовый шаг раскрывается (итог агента, «Decided on the way», изменённые файлы с диффом); «Auto-decided N» в конце — решения агента с «Change».

### 3.5. Карточка вопроса — центральная механика
- Вопрос раскрыт **на своём шаге плана**, так видно, где в задаче мы находимся.
- Метка «Blocking» (терракота) / «Can wait» (приглушённо).
- У каждого варианта **цена · время · обратимость**, у цены и времени — подсказка с источником. «Recommended» помечен, но **ничего не выбрано заранее**: предвыбор подталкивает соглашаться не читая.
- **Выбор варианта сразу перестраивает план ниже** (предпросмотр): новые шаги с плашкой «New», уходящие зачёркнуты с «Removed», изменённые получают новую формулировку. Плашки нейтральные, без цвета.
- **Other** (свой ответ) → агент готовит изменение плана («drafting the plan change…») → «Apply». Свободный текст проходит тот же механизм патча, что и варианты, а автором в журнале остаётся человек.
- **Ask about it** — уточняющий вопрос о вопросе, ответ агента появляется под ним, вопрос остаётся открытым.
- После ответа задача уходит из группы, панель открывает следующую.

### 3.6. Микро-онбординг
- Первый запуск открывает Up next: это главный вопрос приложения.
- Через 1,5 с после загрузки (сначала человек видит экран, потом объяснение) появляется **модалка-приветствие** «Which task to go to first» с рисунком из трёх строк задач и кнопками «Skip» / «Show me around».
- **Тур коучмарками:** группы → панель задачи (вопрос на шаге, цена · время · обратимость) → сводка «While you were away» → режим внимания. Работают клавиши ←/→, Enter, Esc.
- **Подсказка у «Plan»** при первом заходе в чат задачи, один раз на все чаты.
- Всё показывается один раз («тише со временем»); `/up-next?intro` показывает заново для демо.

## 4. Уровни задачи в чате

**Идея:** экран чата Claude Code остаётся основой. Элементы задачи появляются, только когда задаче есть что в них показать. Всё начинается как обычный чат.

| Уровень | Когда | Что добавляется к чату |
|---|---|---|
| 0 · чат | вопрос, объяснение, мелкая правка | ничего |
| 1 · S | маленькая задача | кнопка «Plan» (только читать), бриф — если есть что сказать; в конце карточка результата: 2–3 утверждения с доказательствами, «Review the change» (дифф, скриншоты до/после, проверки), «Accept» |
| 2 · M | задача | кнопка «Plan», план без этапов, бриф — если есть что сказать, допущения, один гейт приёмки |
| 3 · L+ | большая или рискованная | Plan и Brief, этапы и гейты, прогноз против лимита |

- **Видимость — не уровень.** Уровень решает, что задача *просит* у человека, а не что в ней можно *прочитать*. Три вещи, которые раньше включались вместе, разведены:
  - **План** — у любой задачи, только для чтения: что агент делает, сколько стоит, сколько ещё. Он ничего не просит, поэтому не шумит.
  - **Бриф** — когда агенту есть что сказать сверх сообщения человека: что он нашёл в коде или что допустил. Ясная мелкая задача брифа не получает: он пересказал бы запрос, и человек отучился бы читать брифы там, где в них важное.
  - **Гейт** — только по размеру и риску, как раньше.
  - *История для слайда:* решение появилось после показа прототипа — вопрос «почему бриф и план есть не везде?». Ответ «наполовину да»: план — везде, бриф — по содержанию, гейт — по риску. Пример пары: «Прокрутка в длинных чатах» (план, без брифа) и «Дата рождения сдвигается на день» (план и короткий бриф с находкой и безопасным допущением, подтверждать нечего).
- **Уровень = максимум из размера и риска.** Размер оценивается по истории похожих задач, риск — по зоне: платежи, авторизация, миграции, необратимые действия. Маленькая, но рискованная задача всё равно получает бриф и гейт.
- **Вверх — только с согласия, вниз — только по просьбе.** Если задача выросла (план вырос, прогноз перевалил лимит, агент дошёл до миграции), агент присылает **эскалацию**: «Split it into 3 stages?» → «Split into stages» (сделанное сохраняется, дальше согласуешь по ходу) или «Finish as is». «Finish as is» отказывается от брифа и плана, **но не от границ**: иначе кнопка означала бы «одобрить всё».
- **Подсказка уровня до отправки (S2):** над композером тихая строка. Пустое поле — «3 blocked on you · 2 can wait · Up next →», с черновиком — догадка вроде «Looks like a large task (payments) — I'll put together a brief and plan first» + «Just do it». Плейсхолдер нейтральный: бриф обещать нельзя, уровень 0 его не получит.
- **Лимиты задачи («конверт автономии»):** сумма ($12), пути (что агент правит, читает, не трогает), действия. В интерфейсе показаны как «~$6–11 of the $12 limit» и строки доступа в брифе. Чип лимитов в композере пробовали и убрали.

### 4.1. Панель решений над композером (DecisionDock)
**Все решения чата — в одном месте, по одному, в форме вопроса Claude Code:** вопрос в шапке, варианты нумерованными строками (клавиши 1–9), «Other» с полем в строке, Skip / Submit.

Порядок очереди: эскалация → рискованные допущения («Confirm this assumption?» · Confirm / Correct it) → гейт («Approve the brief and plan?» · Approve and start / Edit first, с прогнозом против лимита) → вопросы агента (сначала блокирующие) → приёмка результата.

Почему так: люди уже знают этот паттерн по самому Claude Code; одна форма для пяти видов решений вместо разных наборов кнопок; можно отвечать с клавиатуры. Бриф и план при этом **только для чтения**: мест для решений стало слишком много, их свели в одну очередь.

**Правки текстом до запуска** («Apple Pay не нужен») применяются сразу и видны на месте: допущение в брифе зачёркнуто с «you: …», шаг плана с «Removed», итог пересчитан. До запуска откат дешёвый, поэтому без шага «Apply».

## 5. Plan и Brief — панель рядом с чатом

**Вход:** справа в заголовке чата иконка задачи и слово **«Plan»**. У идущей задачи рядом прогресс «Plan · 3/6 · by 17:30». Открывает панель, в шапке которой название, описание и табы **Plan | Brief**. План идёт первым: человек решает, отпускать ли агента, по тому, что будет сделано и сколько это стоит; бриф объясняет почему. В ленте, когда план готов, появляется плитка-артефакт «Plan · 3 stages · 2 approvals · ~$6–11 of $12».

### 5.1. Plan
- **Три карточки сводки** сверху: сделано «8 of 13», потрачено «$7.70 of $15», время работы агента «2h 54m of ~5h» и «by 20:00». В карточках только факты и шкала, прогноз вынесен в подсказки.
- **Этапы** («1 · Scope → 2 · Build → 3 · Verify») с прогрессом и суммой; у ещё не начатого этапа детали видны только при наведении.
- **Шаги:** сделанный раскрывается (итог, решения по ходу, файлы с диффом). У шага впереди — намерение агента одной фразой, **без списка файлов** (заранее он читался бы как обещание) и только у ближайших шагов (про дальние детали агент ещё не знает).
- **Гейты** — те же точки, кто согласует, сказано текстом («You approve the brief and plan», «Check: checkout tests pass»).
- **Plan rules** внизу: «I change myself: subtasks and their order within a stage. I'll ask about: a new stage or gate, scope, anything over +$2». Это единственное место, где сказано, что план может меняться.
- **Параллельные шаги:** Blocked не значит «задача стоит». Пока шаг ждёт ответа, независимые шаги делают другие агенты: «In parallel · doesn't need your answer», у зависимых — «Starts after your answer on …». В живом статусе ленты — «While you decide: … · +1 in parallel».

### 5.2. Brief
1. **How I understood the task** — 2–3 строки словами агента.
2. **What I found · checked in code and data** — 3–5 проверенных фактов с источниками. Идут раньше допущений: факты проверены, допущения нет.
3. **Assumptions · N to confirm** — рискованные с терракотовой точкой и «Waiting for you in the chat · причина»; безопасные списком «No need to confirm: checked in code or easy to undo».
4. **What I won't touch** — границы словами агента и строки доступа **Edits / Read only / Won't touch** с путями.
5. **Done when · M of N met** — критерии готовности с пустыми кольцами, а не чекбоксами: отмечает их агент с доказательством. У защищённых критериев замок («I can't loosen or skip this»); критерий, добавленный человеком, защищается автоматически.

### 5.3. Лента чата
- **Живой статус** задачи с планом: карточка «Plan · 3/6 · Now: Карточки товаров», по клику открывается план.
- **Вопросы в сообщениях агента** отбиты полосой слева и меткой Blocking / Can wait (терракота, пока блокирующий ждёт). Ответ — в панели решений, в ленте после него «✓ Your answer: … · Change».
- **Чат открывается внизу** и следует за лентой, пока ты там.

### 5.4. Типографика
Весь чат (лента, панель решений, панель задачи) набран одним кеглем 14/20, подписи — 12. В панели четыре роли текста (Title, Heading, Body, Meta), два начертания и три цвета. Отступы растут ступенями: 2 → 6 → 8 → 12 → 18 → 20px. Проверено по всем 17 чатам.

## 6. Приёмка результата (уровни 2–3) — последняя фича, за фиче-тогглом

**Идея:** реестр заявлений, где видна граница между «агент сказал, что сделал» и «это проверил кто-то другой». **Проверяет система, а не агент:** отметку «доказано» даёт только внешний источник (CI, дифф тестов, скриншот, агент-ревьюер). Слова агента никогда не становятся отметкой. Это ответ на вопрос из §0: можно ли доверять словам агента «я всё сделал».

**Фиче-тоггл.** Флаг `acceptance` в `src/data/features.ts`, по умолчанию включён; выключить — `?feature-acceptance=off`, вернуть — `=on` (выбор запоминается в браузере). Флаг проверяется в одном месте, в сцене приёмки в сторе; всё остальное (панель, док, плитка, Up next, сайдбар) вычисляется оттуда, поэтому одна проверка выключает фичу целиком, и чат возвращается к прежнему виду.

### 6.1. Где что
- **Лента** — только слова агента и плитка «Review the result · 7 claims · 2 flags · 1 file outside the brief».
- **Доказательства** — в той же панели задачи, что план и бриф: на приёмке у неё вкладки **Plan | Brief | Result | Diff**. Отдельную панель ревью пробовали и убрали: результат, план и бриф — один объект, между ними переходят одним кликом.
- **Решение** — в доке над композером, как все решения чата.
- **Up next** — задача на приёмке в Can wait (серая неподвижная точка: агент закончил и никого не держит), с нарушенным защищённым критерием — в Blocked; в плане под «You approve the result» та же карточка решения и «Details», ведущий в чат.

### 6.2. Вкладка Result, сверху вниз (доказательства первыми, дифф последним)
1. **Флаги** — «Found 2 things the agent didn't mention»: то, что система нашла сама, а агент промолчал («Skipped test “declines without consent”», «Changed a file outside the brief»). Строки на мягкой подложке с терракотовой точкой, клик открывает файл во вкладке Diff.
2. **Done when · 3 of 6 met** — те же критерии, что в брифе; нарушенный защищённый — терракотой «Broken: test skipped».
3. **Claims** «4 proven · 2 only claimed · 1 contradicted» — сгруппированы по шагам плана, самые рискованные зоны сверху. **Статус значком:** галочка — доказано внешним источником, пустое кольцо — только слова агента, крестик — опровергнуто. Под заявлением — его источник («CI · run #412», «Only claimed», «Contradicts: test skipped»); клик раскрывает само доказательство на месте: лог CI, кусок диффа тестов, скриншоты, слова ревьюера.
4. **Tests** — итог в заголовке, ссылка на прогон CI с логом, тесты по файлам с «new · 5 passed · 1 skipped», пропущенный тест — под своим файлом.
5. **Nobody checked** — честный список того, что никто не проверял и не может проверить автоматически.
6. **Check by hand · 0 of 3 checked** — единственные чекбоксы в продукте: это проверки человека, а не отметки агента.
7. **Risk by area** — зоны (Payments, Tests, Orders) с числом файлов, уровнем риска и самими файлами. Считаются по путям и границам брифа, а не со слов агента.
8. **Why I chose this** — 3–5 строк «выбрал X, потому что Y», без самовосхваления.

### 6.3. Решение в доке
«Accept the result?» · 1 Accept (задача закрыта, план и лог становятся описанием PR) · 2 Send back with the facts (факты подставляются сами: «1 skipped test, 1 file outside the brief», можно дописать своё) · 3 Look deeper first (только когда есть на что смотреть; открывает первое непроверенное заявление, решение остаётся открытым) · Other.

**Защита от бездумного принятия:**
- пока нарушен защищённый критерий, Accept недоступен: «Blocked: a locked criterion is broken», ссылка ведёт на строку критерия;
- «(Recommended)» зависит от состояния: всё доказано → Accept, есть флаги или непроверенное в рискованной зоне → Look deeper first, Accept заблокирован → Send back;
- **у Accept нет клавиши, пока он не рекомендован** — принять результат с флагами одной клавишей нельзя.

### 6.4. Раунды
После Send back в ленте «Sent back: …», задача уходит в Running, в плане появляется шаг «Исправить по итогам приёмки». Следующий раунд показывает разницу, а не всё заново: «Round 2 · 3 files changed since you last looked», у изменившихся заявлений «Was: only claimed». После Accept — «Accepted · PR description ready», задача уходит из Up next, точка в сайдбаре гаснет.

### 6.5. Как делали (история для слайда)
- ТЗ легло в существующий концепт почти целиком: модель, стор, док и панель уже были, новым стало по сути только содержимое вкладки Result. Параллельных сущностей не заводили: `Task.result` получил раунды приёмки, а `Claim` общий с маленькими задачами уровня 1.
- Тексты вычитал UX-писатель («Round» вместо «Iteration», «Was:» вместо «Before:»); два его предложения отклонили — «Not checked yet» обещало бы проверку, которой не будет.
- Визуал дважды правил UI-дизайнер: терракотовую рамку баннера заменили строками флагов, таблицу из двух колонок — шагами плана (не разваливается на узкой панели), число кеглей и цветов свели к ролям панели.
- Значки статуса выбирали по двум макетам рядом: «статус словом» против «статус значком». Выбрали значки — сканируются взглядом, а ТЗ запрещает галочку только без внешнего источника.
- Русскую цитату критерия убрали из строки «Blocked: …» — внутри английской фразы получалась мешанина языков.

## 7. Сайдбар и прочее

- **Проекты и чаты:** чаты сгруппированы по проектам (`storefront`, `astrology-app`, `yango-prototype`). Статус чата живой и берётся из того же состояния: Blocked — терракотовая точка; идёт — серая пульсирующая; результат ждёт принятия — серая; обычный чат — кольцо. Свёрнутый проект с заблокированной задачей внутри показывает терракотовую точку.
- **Up next** — первый пункт навигации, терракотовая точка без числа, если есть Blocked (число только шумело). Иконка-лоток с анимацией при наведении.
- **Строка лимита недели** над аватаром: «52% of weekly limit», при наведении карточка с сессией, неделей и прогнозом «по темпу последних 3 дней».
- **Статус внимания на аватаре** (Busy — кольцо, Do not disturb — точка с чертой), клик открывает то же меню, что в шапке Up next.
- **Routines** — страница с шаблонами регулярных задач агентов (Briefing, Email triage, PR review digest, Flaky test tracker и др.).
- **`/tokens`** — живой справочник дизайн-токенов и каталог иконок.

## 9. Ключевые решения — «пробовали → выбрали → почему»

Подходит для слайда о процессе: видно, что решения проверялись, а не придумывались.

| Выбрали | Отказались от | Почему |
|---|---|---|
| Название **Up next** | Inbox, Needs you, Decisions, Tasks, Queue… | Название вопроса «куда идти первым»; покрывает и Running; «Inbox» обещает inbox zero |
| Три группы Blocked / Can wait / Running | Одна «Needs you» | Смешивались «агент стоит» и «агент идёт, вопрос подождёт» |
| Вопрос на шаге плана | Вопрос наверху панели | Видно, где в задаче мы находимся |
| Предпросмотр последствий прямо в плане | Список «If you choose this» в карточке | Последствия на своих местах, без дублирования |
| Ничего не выбрано заранее | Предвыбран рекомендованный | Предвыбор подталкивает соглашаться не читая |
| Все решения чата — одна панель над композером в форме вопроса Claude Code | Кнопки под брифом в ленте, решения во вкладках | Одна очередь решений, знакомый паттерн, клавиатура |
| Бриф и план — только чтение, в панели справа | Табы «Chat · Brief · Plan» над лентой | Лента не должна подменяться |
| Кнопка «Plan», план первым | «Brief and plan», бриф первым | План отвечает на «отпускать ли агента» (решение вместе с UX-писателем) |
| План у любой задачи, бриф — по содержанию, гейт — по риску | План и бриф только с уровня 2–3; бриф и гейт у каждой задачи | План ничего не просит и полезен всегда; бриф-пересказ учит не читать брифы; гейт на мелочи делает агента бюрократом |
| Только точки и кольца | Галочки, ромбы у гейтов, пауза | Одна система форм на весь продукт |
| Галочка у заявления — только при внешнем источнике (единственное исключение) | Точки и кольца в приёмке; статус словом без значков | Точка и кольцо значили сразу «шаг», «доказано» и «впереди» — было непонятно, готов ли пункт |
| Result и Diff — вкладки панели задачи | Отдельная панель ревью | Один объект — одна панель; две панели по очереди путали |
| Терракота только у «нужен ты» | Терракота у Can wait | 7 оранжевых точек, 2 у работающих задач: акцент перестал выделять |
| «Done when» кольцами | Чекбоксы | Отмечает агент с доказательством, а не человек |
| Без файлов у будущих шагов | «Works in: …» | Список файлов заранее читался как обещание |
| Blocked + параллельные шаги | Отдельная группа «Blocked, still working» | Вопрос блокирующий, путать с Can wait нельзя |
| Проверяет система, а не агент | Отметки со слов агента | Граница «сказал / проверено» — смысл приёмки |
| У Accept нет клавиши, пока он не рекомендован | Перенести Accept вниз списка | Нельзя принять результат с флагами одной клавишей |
| Тексты без жаргона: «limits», «Approve and start», «confirm» | «envelope», «gate», «your gate» | Вычитка UX-писателя: «гейт» и «конверт» — внутренний жаргон |

## 11. Ограничения прототипа и что дальше

- Состояние не сохраняется между перезагрузками (кроме онбординга и ширины панелей).
- Свой ответ и «Ask about it» дают заготовленные ответы агента; «Change» у решений агента и «Reconnect» данные не меняют.
- Правки текстом в чате распознаются по ключевым словам.
- У уровня 2 нет отдельного демо-чата (модель и компоненты его поддерживают).
- Приёмка уровней 2–3 — за тогглом (включён); сцена приёмки живёт в памяти страницы, демо входит в неё по `?scene=acceptance`. Ветка `feature/acceptance`, в `main` пока не влита.
- Следующие шаги: дать чатам задач из Up next ту же кнопку «Plan»; пройденные согласования сделать раскрываемыми; действия у проекта и ветки в мете панели.
